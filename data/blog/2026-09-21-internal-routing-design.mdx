## 상황

서버 간 호출에서 이런 timeout 에러가 나고 있었다.

```
netty ... recvAddress(..) failed: Connection timed out
WebClientRequestException: Request to POST https://<외부 API 도메인>/... 
```

에러를 따라가 보니 이상한 점이 있었다.
같은 내부망에 있는 서비스끼리 호출하는데, 호출 경로가 외부 사용자의 호출과 같았다.

```
서비스 A (EC2) → 외부 공개 도메인 → API Gateway / ALB → Target Group → 서비스 B (EC2)
```

내부에서 내부로 가는 호출이 외부 공개 진입점을 한 번 나갔다가 다시 들어오고 있었다.

---

## 왜 문제인가

- **불필요한 홉이 늘어난다.** 바로 갈 수 있는 길을 돌아간다.
- **외부 구간에 의존하게 된다.** 도메인, DNS, API Gateway 같은 공개 경로에 문제가 생기면 내부 호출도 같이 영향을 받는다.
- **장애 지점이 늘어난다.** 거치는 구성 요소가 많을수록 실패할 곳이 많다.

timeout의 직접 원인이 이 구조라고 확정한 건 아니다.
SSL 문제일 가능성도 있었지만 그것이 원인이라고 확인되지는 않았다.
다만 외부 경로를 거치는 구조에서 timeout 가능성이 커진다고 판단했고,
원인이 무엇이든 내부 호출은 내부 경로로 가는 게 맞다고 정리했다.

---

## 목표로 삼은 것

방안을 비교하기 전에 기준을 먼저 정했다.

1. 내부 호출이 외부 경로를 타지 않을 것
2. 이중화가 유지될 것
3. 호출 경로가 단순할 것
4. 현재 구조와 운영 난이도를 함께 고려할 것

외부 사용자의 호출은 기존 API Gateway를 그대로 쓰고, 내부 호출만 분리하는 방향이다.

---

## 방안 3가지

### 1. internal NLB

내부 전용 Network Load Balancer를 두고 TCP 레벨에서 전달한다.

- 장점: 단순하고 빠르다. 내부 이중화에 맞고, SSL 인증서의 이름 일치를 신경 쓰지 않아도 된다.
- 단점: 경로(Path)나 호스트(Host) 기반 라우팅이 안 된다. 서비스가 늘면 포트 관리가 복잡해질 수 있다.

### 2. internal ALB + Route 53 private DNS

내부 전용 ALB를 두고 Route 53 프라이빗 호스팅 영역으로 내부 전용 이름을 붙인다.

- 장점: 내부 HTTP API 구조에 가장 잘 맞는다. 도메인 기반으로 정리되고 확장이 쉽다.
- 단점: private DNS 구성과 운영 정책이 필요하다. 상대적으로 복잡하다.

### 3. internal ALB + 기존 외부 DNS에 CNAME 등록

내부 ALB를 두되 이름은 기존 외부 DNS에 등록하는 방식이다.

- 장점: 지금 쓰는 DNS 방식과 비슷해서 익숙하다.
- 단점: 내부 전용 이름이 공개 DNS에 노출되고, 내부용과 외부용 이름 체계가 뒤섞인다.

---

## 배제한 방법 — hosts 파일

각 서버의 `hosts` 파일에 내부 주소를 직접 적는 방법도 있었다.
당장은 가장 빠르지만 선택하지 않았다.

- 서버마다 따로 관리해야 한다.
- 변경 이력이 남지 않아 재현과 롤백이 어렵다.
- 서버가 늘수록 관리 대상이 함께 늘어난다.

단기 패치일 뿐 문제를 구조적으로 해결하지 못한다고 판단했다.
내부 LB와 private DNS는 인프라 수준에서 한 번 만들어두면 재현, 롤백, 확장이 모두 쉬운 구조가 된다.

---

## 결론

| | 방안 | 이유 |
| --- | --- | --- |
| 단기 | internal NLB | 가장 단순하고 빠르게 적용할 수 있다 |
| 장기 | internal ALB + private DNS | 도메인 기반으로 가장 깔끔하게 정리된다 |

정리하면 **지금 당장은 internal NLB, 구조를 정돈하려면 internal ALB와 private DNS**였다.
이 방향으로 내부 트래픽을 VPC 안에서 직접 라우팅하는 설계를 정리해 제안했다.

이 글은 설계와 제안까지의 기록이다.
실제 인프라 적용은 후속 작업으로 남아 있다.

---

## 정리

- 내부에서 내부로 가는 호출은 **외부 공개 경로를 거치지 않게** 나눈다.
- 방안을 비교하기 전에 판단 기준(외부 경로 회피, 이중화, 단순함, 운영 난이도)을 먼저 정한다.
- 서버마다 `hosts`를 고치는 방식은 빠르지만, 재현과 롤백이 안 돼서 구조적 해결이 되지 않는다.
- 원인이 확정되지 않았더라도, 구조상 불필요한 경로라면 그 자체로 고칠 이유가 된다.
