## 배경

AWS IoT OTA로 디바이스에 펌웨어를 배포하고 있었지만,
펌웨어에 서명을 하고 디바이스가 그 서명을 검증하는 체계가 없었다.

서명이 없으면 누가 만든 펌웨어인지, 배포 중에 바뀌지 않았는지를 디바이스가 확인할 방법이 없다.
그래서 OTA 경로에 올라가기만 하면 인증되지 않은 펌웨어도 그대로 배포될 수 있는 상태였다.

이 글은 코드사이닝 인프라를 처음부터 구축한 과정을 정리한 것이다.

---

## 전체 구조

```
[로컬] OpenSSL로 개인키 + 인증서 생성
    ↓ import
[ACM] 인증서 보관
    ↓ 인증서 ARN 참조
[AWS Signer] 서명 프로파일
    ↓ 서명 작업
[S3] 서명된 펌웨어 (버전 관리)
    ↓
[IoT Job / Stream] 디바이스로 배포
    ↓
[디바이스] 등록 시점에 받아둔 공개키로 서명 검증
```

핵심은 **개인키로 서명하고, 공개키로 검증한다**는 신뢰 체인이다.
서명하는 쪽(AWS)과 검증하는 쪽(디바이스)이 서로 다른 키를 들고 있고,
두 키가 한 쌍이라는 것만 맞으면 펌웨어의 출처와 무결성을 확인할 수 있다.

---

## 1. OpenSSL로 키와 인증서 만들기

서명에 쓸 키는 ECDSA P-256으로 만들었다.
인증서 요청 설정 파일에서 **용도를 `codeSigning`으로 명시**했다.

```
keyUsage         = digitalSignature
extendedKeyUsage = codeSigning
```

인증서에 용도를 못 박아두면 이 키가 TLS 서버 인증 같은 다른 용도로 쓰이는 것을 막을 수 있다.
서명 키는 유출되거나 오용됐을 때 영향이 크기 때문에 처음부터 범위를 좁혀두는 편이 안전하다.

이후 개인키와 X.509 인증서(유효기간 365일)를 생성했다.

```bash
# 개인키 (EC P-256)
openssl genpkey -algorithm EC -pkeyopt ec_paramgen_curve:P-256 -out ecdsasigner.key

# 자체 서명 인증서
openssl req -new -x509 -config cert_config.txt -key ecdsasigner.key \
  -out ecdsasigner.crt -days 365
```

---

## 2. ACM에 import

만든 키와 인증서를 AWS Certificate Manager에 import한다.

```bash
aws acm import-certificate \
  --certificate fileb://ecdsasigner.crt \
  --private-key fileb://ecdsasigner.key
```

ACM에 등록하는 이유는 **AWS Signer가 서명할 때 ACM에 있는 인증서를 ARN으로 참조하기 때문**이다.
서명 프로파일에 이 ARN을 지정해두면, 서명 요청은 IAM 권한이 있는 주체만 보낼 수 있다.
개인키 파일을 여러 사람이 나눠 갖지 않고도 서명 권한을 통제할 수 있다는 점이 이 구조의 장점이다.

---

## 3. Signer 프로파일 등록

서명 프로파일에는 어떤 인증서로, 어떤 플랫폼 규격으로 서명할지를 지정한다.

```bash
aws signer put-signing-profile \
  --profile-name ota_signer \
  --signing-material certificateArn=<ACM 인증서 ARN> \
  --platform AmazonFreeRTOS-Default
```

이후 펌웨어 서명 작업은 이 프로파일 이름으로 요청한다.

---

## 4. S3 버킷

서명 전 펌웨어 바이너리를 올리고, 서명된 결과물이 저장되는 버킷이다.

펌웨어는 어떤 버전이 언제 배포됐는지 추적할 수 있어야 해서 **버전 관리를 켰다.**
버킷 정책에는 OTA 실행 역할과 S3 로깅 서비스의 접근만 허용했다.

---

## 5. IAM 역할

OTA 파이프라인의 각 단계가 서로 호출할 수 있도록 실행 역할을 만들었다.
권한은 파이프라인 전 단계에 필요한 것만 부여했다.

- S3 (펌웨어 읽기/쓰기)
- Signer (서명 작업)
- IoT Job / Stream (배포)
- CloudWatch (로그)
- IAM PassRole

---

## 6. 공개키 추출

디바이스가 서명을 검증하려면 개인키와 한 쌍인 공개키가 필요하다.
개인키에서 공개키만 추출한다.

```bash
openssl ec -in ecdsasigner.key -pubout -out ecdsasigner.pub
```

공개키는 디바이스를 등록하는 시점에 전달되고, 디바이스가 이를 저장해두었다가 OTA 때 검증에 사용한다.

---

## OTA 테스트 중에 발견한 문제

인프라를 만들고 OTA를 테스트하는 과정에서 이상한 동작을 발견했다.
새로운 모델의 인증서를 발급해 OTA를 진행할 때,
**공개키를 디바이스에 전달하지 않았는데도 업데이트가 그대로 진행됐다.**

디바이스가 서명이나 키를 확인하지 않고 업데이트하고 있었다는 뜻이다.
서버 쪽에 서명 파이프라인이 완벽해도, 디바이스가 검증하지 않으면 서명은 아무 의미가 없다.

이 내용을 디바이스 담당자에게 전달했고, 함께 확인해 해결했다.
이 일 이후로 "서명을 만든다"와 "서명이 검증된다"를 별개로 확인해야 한다는 걸 기준으로 삼게 됐다.

---

## 신규 제조사 키 발급

인프라를 만든 뒤에는 제조사가 추가될 때마다 키를 발급해야 한다.
발급 절차는 아래 순서다.

1. 개인키 생성, 인증서 발급
2. ACM import
3. Signer 프로파일 등록
4. IAM 정책에 새 Signer ARN 반영
5. 공개키 추출 후 DB 등록용 SQL 준비

운영하면서 알게 된 점도 있다.

- **운영 계정은 MFA 없이는 접근이 거부된다.** `AccessDenied`가 뜨면 MFA 세션 토큰을 먼저 발급받아 진행해야 한다.
- **인증서를 지우기 전에 재사용 여부를 확인해야 한다.** ACM 인증서가 다른 서비스(예: ALB)에서 쓰이고 있을 수 있어서, 삭제 전에 `InUseBy`를 확인했다.
- **인증서 유효기간이 365일이라 만료 관리가 필요하다.** 만료된 리소스가 쌓이면 어떤 프로파일이 실제로 쓰이는지 알기 어려워진다.

이 절차는 지금 수동으로 진행한다.
반복되는 작업이라 자동화 도구를 만들어 테스트해뒀지만, 화면이 없어서 실제 운영에는 적용하지 않았다.
제조사 수가 늘어 필요해지면 바로 쓸 수 있는 상태다.

---

## 정리

코드사이닝은 서명을 만드는 일이 전부가 아니었다.

- **누가 서명할 수 있는가** — 키를 ACM에 두고 IAM으로 통제
- **키를 어디에 쓸 수 있는가** — 인증서 용도를 `codeSigning`으로 제한
- **디바이스가 실제로 검증하는가** — 서명 체계를 만든 뒤에도 끝까지 확인

이 세 가지가 함께 맞아야 "서명된 펌웨어만 배포된다"는 말이 성립한다.
