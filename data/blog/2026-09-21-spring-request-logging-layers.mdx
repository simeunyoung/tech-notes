## 배경

기존에는 대부분의 로그를 Service 계층에서 `log.info()`로 직접 찍고 있었다.
이 방식에는 불편한 점이 계속 있었다.

- 요청 하나가 어떤 흐름으로 처리됐는지 로그만 봐서는 이어 붙이기 어렵다.
- 같은 요청에 대해 Controller와 Service에서 비슷한 로그가 중복으로 나온다.
- 로깅 코드가 비즈니스 로직 사이에 끼어들어 코드 읽기가 불편하다.
- 요청과 응답 전체를 보고 싶을 때 볼 곳이 없다.

로그를 더 찍는 게 아니라 **어디서 무엇을 찍을지 역할을 나누는 쪽**으로 정리하기로 했다.

---

## 역할 나누기

로그를 세 계층으로 나눴다.

| 계층 | 하는 일 |
| --- | --- |
| Filter | 요청, 응답 Body를 메모리에 캐싱하고 DEBUG일 때만 출력 |
| Interceptor | 요청 시작과 끝의 메타 정보 기록, `traceId` 생성 |
| Service | 비즈니스 의미가 있는 로그만 유지 |

Interceptor가 요청 수신 로그를 맡으니 Service에 있던 "요청 받았음" 로그는 지웠다.
Service에는 실제로 의미 있는 상태(처리 결과, 경고, 오류)만 남긴다.

---

## Interceptor — 항상 필요한 정보만

운영에서 항상 있어야 하는 건 **요청이 들어와서 나갈 때까지의 요약**이다.
Interceptor에서 요청이 시작될 때 메서드, URI, IP를 남기고, 끝날 때 상태 코드와 처리 시간, 예외를 남긴다.
여기서 요청마다 `traceId`를 만들어 MDC에 넣는다.

```java
// 구조를 보여주기 위한 예시
@Override
public boolean preHandle(HttpServletRequest request, HttpServletResponse response, Object handler) {
    MDC.put("traceId", UUID.randomUUID().toString().substring(0, 8));
    log.info("[REQ] {} {} {}", request.getMethod(), request.getRequestURI(), request.getRemoteAddr());
    request.setAttribute("startTime", System.currentTimeMillis());
    return true;
}

@Override
public void afterCompletion(HttpServletRequest request, HttpServletResponse response,
                            Object handler, Exception ex) {
    long duration = System.currentTimeMillis() - (long) request.getAttribute("startTime");
    log.info("[RES] {} {}ms", response.getStatus(), duration);
    if (ex != null) {
        log.error("요청 처리 중 예외", ex);
    }
    MDC.clear();
}
```

`traceId`가 MDC에 들어 있으니 이 요청 안에서 찍히는 모든 로그(Service 포함)에 같은 값이 붙는다.
로그에서 `traceId` 하나로 검색하면 요청 하나의 흐름이 한 번에 나온다.

Body는 Interceptor에서 찍지 않는다. 이유는 아래에 있다.

---

## Filter — Body는 한 번만 읽을 수 있다

요청과 응답의 Body까지 볼 수 있으면 디버깅이 훨씬 쉽다.
그런데 HTTP 요청 Body는 **한 번만 읽을 수 있다.**
Interceptor나 로깅 코드에서 먼저 읽어버리면 Controller가 Body를 받지 못한다.

그래서 Filter에서 요청과 응답을 캐싱 래퍼로 감쌌다.

```java
// 구조를 보여주기 위한 예시
public class BodyCachingFilter extends OncePerRequestFilter {

    @Override
    protected void doFilterInternal(HttpServletRequest request, HttpServletResponse response,
                                    FilterChain chain) throws ServletException, IOException {
        ContentCachingRequestWrapper req = new ContentCachingRequestWrapper(request);
        ContentCachingResponseWrapper res = new ContentCachingResponseWrapper(response);
        try {
            chain.doFilter(req, res);
        } finally {
            if (log.isDebugEnabled()) {
                log.debug("[REQ BODY] {}", new String(req.getContentAsByteArray(), UTF_8));
                log.debug("[RES BODY] {}", new String(res.getContentAsByteArray(), UTF_8));
            }
            res.copyBodyToResponse();
        }
    }
}
```

두 가지가 중요했다.

- **Body는 요청이 처리된 뒤에 읽는다.** 래퍼는 누군가 Body를 읽을 때 그 내용을 복사해 둔다. 그래서 `chain.doFilter()`가 끝난 뒤 `finally`에서 꺼낸다.
- **`copyBodyToResponse()`를 반드시 호출해야 한다.** 응답 래퍼는 Body를 자기 안에 모아두기 때문에, 마지막에 원래 응답으로 복사해주지 않으면 클라이언트는 빈 응답을 받는다.

---

## Body 로그는 DEBUG에서만

Body 로그는 DEBUG 레벨일 때만 찍도록 제한했다.

- **개인정보가 들어 있을 수 있다.** 비밀번호, 토큰이 요청 Body에 실린다.
- **로그 용량이 급증한다.** 모든 요청과 응답을 통째로 남기면 금방 커진다.
- **직렬화와 IO 비용이 든다.** 요청마다 Body를 문자열로 만들고 쓰는 비용이 있다.
- **가독성이 떨어진다.** 평소 로그에 Body가 섞이면 정작 봐야 할 로그가 묻힌다.

평소에는 INFO로 요약만 남겨 가볍게 유지하고,
문제가 생겼을 때 DEBUG를 켜서 Body까지 보는 방식이다.
로그는 많을수록 좋은 게 아니라 역할이 명확해야 한다는 기준으로 나눴다.

---

## 결과

- `traceId` 하나로 요청 단위 흐름이 한눈에 보인다.
- Service 코드에서 로깅이 빠져 비즈니스 로직이 읽기 쉬워졌다.
- 운영 로그(INFO)와 상세 분석 로그(DEBUG)가 분리됐다.

이 구조를 서비스 4개에 공통으로 적용하고 3개 환경에 순서대로 배포했다.

---

## 정리

- 로깅은 **어느 계층이 무엇을 책임지는지**를 나누면 정리된다. Service는 의미를, Interceptor는 요약을, Filter는 원문을 맡는다.
- Body는 한 번만 읽히므로 캐싱 래퍼를 쓰고, 읽는 시점은 요청이 끝난 뒤로 잡는다.
- 응답 래퍼를 쓰면 `copyBodyToResponse()`를 잊지 않는다.
- 상세 로그는 켜고 끌 수 있게 만들고, 개인정보가 들어갈 수 있는 값은 기본으로 찍지 않는다.
