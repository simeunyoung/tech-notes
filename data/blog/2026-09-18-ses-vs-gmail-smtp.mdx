## 배경

담당 서비스에 이메일 발송 기능(상태 변경 알림, 매직링크 인증)을 추가해야 했다.

이 서비스에는 이미 메일 발송이 붙어 있었다.
개인 Gmail 계정을 SMTP 발신 계정으로 쓰는 방식이었고, 발송량이 하루 10통 안팎이라 지금까지 문제는 없었다.
새 기능도 그 계정에 얹으면 코드는 거의 바꾸지 않아도 됐다.

그런데 "이미 돌아가고 있으니 그냥 쓰면 되는 것 아닌가" 하는 생각과
"발송용 서비스인 SES를 쓰는 게 맞지 않나" 하는 생각이 부딪혔다.
팀에서는 "Gmail SMTP는 발송 제한이 없다"는 이야기도 나왔다.
그래서 두 방식을 같은 기준으로 비교해보기로 했다.

---

## SMTP는 프로토콜, Gmail과 SES는 서비스

비교하기 전에 헷갈리기 쉬운 부분부터 정리했다.
**SMTP는 메일을 주고받는 통신 규칙이고, Gmail과 SES는 그 규칙을 지원하는 서로 다른 서비스다.**
"SMTP로 보낸다"는 말은 Gmail이든 SES든 똑같이 성립해서, 둘을 같은 종류의 선택지로 착각하기 쉽다.

| | Gmail (개인 메일함) | AWS SES (발송 전용 서비스) |
| --- | --- | --- |
| 만들어진 목적 | 사람이 메일을 쓰고 받는 것 | 애플리케이션의 자동 발송 |
| 발송 한도 | 고정 상한 | 기본값이고, 요청하면 상향 가능 |
| 한도 계량 | 메시지 수와 수신자 수 중 먼저 차는 쪽 | 수신자 수 |
| 계정 | 다른 용도와 공유하면 한도와 계정 상태를 같이 씀 | 서비스 전용으로 분리 가능 |

## 비교 기준 1 — 발송 한도

### Gmail

| 항목 | 무료 Gmail | Google Workspace |
| --- | --- | --- |
| 하루 발송 메시지 수 | 500통 | 2,000통 (체험판은 500통) |
| 하루 고유 수신자 수 | 명시 없음 | 3,000명 (외부 2,000명) |

무료 Gmail 도움말은 웹, 앱, SMTP 같은 발송 방법을 구분하지 않고 같은 한도를 적용한다.
"SMTP는 예외"라고 볼 근거는 문서에 없었다.
한도를 넘기면 보통 1~24시간 동안 발송이 막힌다.

메시지 하나에 넣을 수 있는 수신자 수는 두 문서의 기준이 달라서 단순 비교하기 어렵다.
무료 Gmail 도움말은 500명이라고만 하고, Google Workspace는 발송 방법에 따라 다르다.
웹에서는 2,000명(외부 500명), SMTP/POP/IMAP은 100명이다.
이 서비스는 신청자 한 명에게 1:1로 보내서 이 한도는 판단에 영향을 주지 않았다.

다른 메일 서비스(Microsoft 365, Yahoo, iCloud 등)도 하루 발송 한도를 둔다.
사람이 쓰는 메일함 서비스 중에 한도가 없는 곳은 없었다.

### SES

- 한도는 **메시지가 아니라 수신자 수** 기준이다. 수신자가 10명인 메일은 10으로 센다.
- 기본값일 뿐이고, AWS Support에 요청하면 올릴 수 있다.
- 처음 계정은 샌드박스 상태라 하루 200통, 초당 1통으로 제한된다. 운영 환경 사용을 신청해서 샌드박스에서 나와야 한다.
- 한 번의 `SendEmail` 호출에 여러 수신자를 넣지 말고, 수신자마다 한 번씩 호출하라고 권장한다. 한 명이 실패하면 메일 전체가 거부되기 때문이다.

이 서비스는 신청자 한 명에게 개별로 보내는 구조라서 SES의 권장 방식과 자연스럽게 맞는다.

## 비교 기준 2 — 한도 근처에서는 어떻게 되나

"제한이 없다"는 말이 실제로 어떤지 궁금해서 Gmail SMTP를 직접 한도 근처까지 밀어봤다.
먼저 밝혀둘 게 있다. 이 테스트는 **실제 사용 패턴과는 거리가 먼 극단적인 실험**이다.
하루 10통 안팎으로 쓰는 서비스가 새 계정에서 2초 간격으로 쉬지 않고 수백 통을 보낼 일은 없다.
그래서 이 결과로 "Gmail은 곧 막힌다"고 말할 수는 없고, 한도가 어떤 식으로 동작하는지 보는 용도로만 봤다.

- 운영 중인 계정으로 하면 서비스 기능이 멈추므로, **발신과 수신 모두 새로 만든 무료 Gmail 테스트 계정**을 썼다.
- Python `smtplib`으로 1통씩 순서대로 보냈다. 간격은 2초였다.
- 실패한 시점의 발송 수와 에러 코드를 기록했다.

```python
import smtplib
from email.mime.text import MIMEText
import time

server = smtplib.SMTP("smtp.gmail.com", 587)
server.starttls()
server.login(SENDER, APP_PASSWORD)

try:
    for i in range(1, 600):
        msg = MIMEText(f"테스트 메일 #{i}")
        msg["Subject"] = f"SMTP 한도 테스트 {i}"
        msg["From"] = SENDER
        msg["To"] = RECIPIENT
        server.sendmail(SENDER, [RECIPIENT], msg.as_string())
        print(f"{i}번째 발송 성공")
        time.sleep(2)
except smtplib.SMTPException as e:
    print(f"실패: {e}")
finally:
    server.quit()
```

### 463통에서 실패

463통까지 성공했고, 464번째에서 이 에러가 났다.

```
421 4.3.0 Temporary System Problem. Try again later.
```

500통 상한에 걸린 줄 알았는데 에러 코드가 달랐다.
하루 한도를 넘기면 보통 `550 5.4.5`(Daily user sending limit exceeded)가 나온다.
`421`은 "일시적인 문제이니 나중에 다시 시도하라"는 임시 오류였다.

| | 예상한 에러 | 실제로 뜬 에러 |
| --- | --- | --- |
| 코드 | `550 5.4.5` | `421 4.3.0` |
| 의미 | 하루 한도 초과, 영구 거부 | 일시적 문제, 재시도 가능 |

이어서 464번부터 다시 시도했더니 이번엔 로그인이 막혔다.

```
SMTPAuthenticationError: (534, b'5.7.9 ... WebLoginRequired ...')
```

앱 비밀번호로는 더 인증되지 않았고, 브라우저에서 직접 로그인해 본인 확인을 해야 다시 쓸 수 있었다.

### 이 테스트로 알게 된 것

- 문서상 500통에 닿기 전에 임시 차단이 걸렸다. 문서에 적힌 숫자가 전부가 아니라는 뜻이다.
- 차단은 발송만 막는 게 아니라 계정 로그인까지 막을 수 있다. 개인 계정에 서비스 기능이 묶여 있으면 그 계정의 상태가 곧 서비스 상태가 된다.
- 반대로 이 서비스의 실제 발송량(하루 10통 안팎)에서 이런 차단이 걸릴 가능성은 낮다. 이 테스트만으로 Gmail을 못 쓴다는 결론은 나오지 않는다.

무료 Gmail 계정으로만 확인했고, Workspace 계정에서 어떻게 동작하는지는 보지 못했다.

## 비교 기준 3 — 계정을 누가 갖고 있나

결국 한도보다 이쪽이 더 큰 차이였다.

- **개인 계정에 묶여 있다.** 계정 주인의 사정(비밀번호 변경, 계정 정지, 퇴사)에 발송 기능이 같이 흔들린다.
- **한도와 계정 상태를 다른 사용과 나눠 쓴다.** 서비스 전용이 아니라 그 계정에서 하는 다른 메일 활동과 같이 묶인다.
- **문제가 생겨도 내가 손댈 수 없다.** Gmail은 한도를 올려달라고 요청할 수 없는 고정 상한이고, 차단이 걸려도 계정 소유자가 풀어야 한다.

SES는 서비스 전용으로 분리해서 쓸 수 있다.
한도는 있지만 고정 상한이 아니라 요청으로 올릴 수 있는 기본값이다.

## 정리

지금 하루 10통 안팎에서는 기존 Gmail 계정도 문제없이 돌아간다.
한도에 걸려서 SES로 가야 하는 상황이 아니고, 이 테스트가 그걸 증명하지도 않는다.

그래도 **SES가 맞다**고 정리했다. 이유는 한도가 아니라 구조다.

| 기준 | 기존 Gmail SMTP | SES |
| --- | --- | --- |
| 계정 | 개인 계정, 다른 용도와 공유 | 서비스 전용으로 분리 |
| 한도 | 고정 상한 (무료 기준 하루 500통) | 기본값, 요청하면 상향 |
| 문제가 생기면 | 계정 소유자가 해결 | 서비스 쪽에서 조정 |
| 발송 방식 | 메일함을 발신 수단으로 빌려 씀 | 애플리케이션 발송용으로 설계됨 |
| 도입 비용 | 이미 붙어 있음 | 샌드박스 해제 등 준비 필요 |

- 알림 종류가 늘고 발송량이 커질수록 개인 계정에 얹은 발송 기능의 위험도 함께 커진다.
- SES는 준비할 게 있지만, 한 번 분리해두면 이후의 한도와 계정 문제를 서비스 안에서 다룰 수 있다.
- "Gmail SMTP는 발송 제한이 없다"는 말은 공식 문서와 직접 테스트 어디에서도 근거를 찾지 못했다.
