## 배경

신규 서비스의 DB 설계서를 쓰면서 두 가지를 고민했다.

- 상태값과 코드값을 **DB 코드 테이블**로 관리할지, **Java Enum**으로 관리할지
- PK와 FK를 **INT**로 할지 **BIGINT**로 할지

처음에는 둘 다 관성대로 잡았다.
상태값은 코드 테이블에, PK는 BIGINT에 두었다.
팀 리뷰를 거치면서 기준을 하나씩 세워 다시 정리했다.

---

## 코드 테이블 vs Enum

두 방식의 차이는 이렇다.

| | 코드 테이블 | Enum |
| --- | --- | --- |
| 값 추가 | 데이터만 넣으면 됨 (배포 불필요) | 코드 수정 후 배포 필요 |
| 코드에서 쓰는 값 | 문자열이나 숫자를 코드와 DB가 각자 들고 있음 | 코드 한 곳에서 관리 |
| 오타, 없는 값 | 런타임에 발견 | 컴파일 시점에 발견 |
| 화면 드롭다운 | DB 조회로 그대로 사용 | 별도 목록 API 필요 |

어느 쪽이 낫다기보다 **값이 어떻게 쓰이느냐**에 달려 있다.
아래 세 가지를 기준으로 판단했다.

**1. 운영 중에 값이 추가될 일이 있는가**
코드 테이블의 가장 큰 장점은 배포 없이 값을 추가할 수 있다는 것이다.
이 서비스에서는 상태값이 운영 중에 늘어나야 한다는 요구가 없었다.
값이 바뀔 때는 어차피 관련 로직도 함께 바뀐다.

**2. 로직이 그 값에 관여하는가**
상태 값이 분기 조건이나 상태 전이 규칙에 쓰인다면,
코드 안에 `"APPROVED"` 같은 값이 그대로 들어간다.
그러면 같은 값을 DB(코드 테이블)와 코드 두 곳에서 관리하게 된다.
한쪽만 바뀌면 조용히 어긋나는 **이중 관리** 문제가 생긴다.

**3. 값의 개수가 안정적인가**
값이 몇 개 안 되고 잘 바뀌지 않는다면 Enum이 부담 없다.
값이 수십, 수백 개로 늘거나 자주 바뀐다면 테이블이 낫다.

세 가지 모두 Enum 쪽이라 **상태값과 코드값 8종을 Java Enum으로 바꿨다.**
DB에는 코드 테이블 없이 컬럼에 값을 저장하고, 의미는 코드가 관리한다.

---

## PK와 FK 타입 — BIGINT에서 INT로

PK를 습관처럼 BIGINT로 잡았는데, 예상 물량을 따져보니 과했다.

- INT는 약 21억까지 담는다.
- 이 서비스에서 예상하는 데이터 규모로는 INT를 넘길 일이 없었다.
- PK와 FK는 인덱스에도 반복해서 저장되기 때문에, 4바이트로 줄이면 테이블과 인덱스 크기가 함께 줄어든다.

그래서 **PK와 FK를 INT로 바꿨다.**
"나중에 커질지도 모르니까 일단 BIGINT"가 아니라
예상 물량을 숫자로 잡아보고 정하는 쪽으로 기준을 바꿨다.

---

## 예외 — 파일 크기는 BIGINT

파일 크기 컬럼만은 BIGINT로 남겼다.
업로드할 파일이 최대 100GB까지 가능한데,
바이트 단위로 저장하면 100GB는 약 1,070억이라 INT 범위(약 21억, 약 2GB)를 훨씬 넘는다.

```
INT     최대 2,147,483,647      ≈ 2GB
100GB   107,374,182,400         → INT로는 저장 불가
```

전부 INT로 통일하려다 이 컬럼만 예외를 두었다.
"일괄적으로 정한다"보다 **컬럼마다 담을 값의 최댓값을 확인하는 것**이 기준이었다.

---

## 정리

- 코드 테이블과 Enum은 우열이 아니라 **값이 바뀌는 방식**에 따라 정한다. 운영 중 추가 여부, 로직 관여 여부, 값의 개수가 기준이다.
- 로직이 값을 직접 쓰고 있다면 DB와 코드에 같은 값이 남지 않도록 한 곳에서 관리한다.
- 컬럼 타입은 습관이 아니라 **예상 물량과 최댓값**으로 정한다.
