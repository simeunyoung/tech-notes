## 배경

신규 서비스를 기존 EC2에 함께 올리고 CI/CD용 Self-hosted Runner까지 구성하면서
용량이 작게 잡혀 있던 개발 서버의 디스크 여유가 부족해졌다.

서버를 새로 구성하는 방법도 있었지만,
문제가 "디스크가 작다"는 한 가지였기 때문에 **볼륨 증설로 범위를 좁혔다.**
고객사 소유 인프라라 임의로 진행하지 않고,
증설 용량(3GB)에 대해 사전에 협의한 뒤 직접 작업했다.

---

## 볼륨, 파티션, 파일시스템

콘솔에서 볼륨 크기를 바꿨다고 서버에서 바로 쓸 수 있는 용량이 늘어나지 않는다.
디스크는 세 겹으로 되어 있고, **각 단계를 따로 늘려야 한다.**

```
EBS 볼륨 (AWS 콘솔)      10GB → 13GB   ← 1. 리사이즈
  └─ 파티션              10GB          ← 2. growpart
       └─ 파일시스템(XFS) 10GB          ← 3. xfs_growfs
```

중간 단계를 건너뛰면 `df -h`에 보이는 사용 가능 용량은 그대로다.

---

## 작업 순서

### 1. 콘솔에서 볼륨 크기 변경

AWS 콘솔에서 해당 볼륨의 크기를 10GB에서 13GB로 수정한다.
볼륨을 분리하거나 인스턴스를 중지하지 않고 사용 중인 상태에서 변경할 수 있다.

### 2. lsblk로 구조 확인

서버에 접속해 디스크와 파티션 구조를 확인한다.

```bash
lsblk
```

```
NAME          MAJ:MIN RM SIZE RO TYPE MOUNTPOINT
nvme0n1       259:0    0  13G  0 disk
└─nvme0n1p1   259:1    0  10G  0 part /
```

디스크(`disk`)는 13GB로 보이지만 파티션(`part`)은 아직 10GB다.
위 출력은 형태를 보여주기 위한 예시이고, 디바이스 이름은 인스턴스 유형마다 다르다.

### 3. growpart (dry-run 먼저)

```bash
sudo growpart --dry-run /dev/nvme0n1 1
```

`--dry-run`은 실제로 바꾸지 않고 어떻게 바뀔지만 보여준다.
파티션 테이블을 건드리는 작업이라 미리 확인하는 습관을 들였다.
이상이 없으면 실제로 실행한다.

```bash
sudo growpart /dev/nvme0n1 1
```

### 4. xfs_growfs

파일시스템 종류를 먼저 확인했다. 이 서버는 XFS였다.

```bash
sudo xfs_growfs -d /
```

XFS는 마운트된 상태에서 늘릴 수 있어서 서비스를 내리지 않아도 된다.

### 5. df -h로 확인

```bash
df -h
```

`/`의 크기가 13GB로 반영된 것을 확인하면 끝이다.

---

## 주의할 점

**XFS는 줄일 수 없다.**
확장은 온라인으로 되지만 축소는 지원하지 않는다.
그래서 "일단 크게"보다 필요한 만큼만 늘리는 편이 좋다.

**같은 볼륨은 한 번 수정하면 일정 시간(6시간) 동안 다시 수정할 수 없다.**
그래서 너무 작게 잡으면 곧바로 다시 늘릴 수 없다.
증설 크기는 앞으로 늘어날 사용량까지 감안해서 정해야 한다.

**작업 전에 스냅샷을 만들어 두는 것을 권장한다.**
파티션 테이블을 다루는 작업이라 만약을 대비한 복구 지점이 있으면 안전하다.

---

## 정리

이번 작업에서 가장 중요했던 건 명령어 자체보다 **"볼륨, 파티션, 파일시스템은 각각 다른 계층"이라는 이해**였다.
이걸 알고 나면 순서(볼륨 → 파티션 → 파일시스템)가 자연스럽게 외워지고,
어느 단계에서 막혔는지도 `lsblk`와 `df -h` 두 명령으로 바로 알 수 있다.

고객사 인프라라는 점도 있었기 때문에,
작업 전 협의 → dry-run → 실행 → `df -h`로 검증하는 순서를 문서로 남겨 다음에 같은 상황이 생기면 재사용할 수 있게 했다.
