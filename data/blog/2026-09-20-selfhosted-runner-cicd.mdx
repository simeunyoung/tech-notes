## 배경

새로 시작한 서비스에는 배포 자동화가 없어서
빌드와 배포를 매번 수동으로 하고 있었다.
프론트엔드와 백엔드 레포가 분리되어 있어서 배포 절차도 두 번이었다.

GitHub Actions로 자동화하는 것이 당연한 선택처럼 보였지만,
서버 환경에 제약이 하나 있었다.

---

## GitHub-hosted 러너를 쓸 수 없었던 이유

개발 서버, 운영 서버, 온프레미스 고객사 서버 **세 환경 모두**
허용된 IP만 접근할 수 있는 정책이 적용되어 있었다.

GitHub-hosted 러너는 실행할 때마다 IP가 바뀌는 GitHub 소유의 인프라에서 돌아간다.
그래서 서버 쪽 방화벽에 러너의 IP를 미리 열어둘 수 없다.

```
GitHub-hosted 러너 (IP 유동)  ──✕──▶  허용된 IP만 접근 가능한 서버
```

방화벽을 GitHub의 IP 대역 전체로 여는 방법은 있지만,
접근 통제를 목적으로 만든 정책을 우회하는 셈이라 선택지에서 뺐다.

---

## CI와 CD를 나누려다 전부 Self-hosted로

설계 초기에는 이런 구조를 생각했다.

- **CI(빌드, 테스트)**: GitHub-hosted 러너에서 실행
- **CD(배포)**: 사설망에 접속해야 하니 Self-hosted 러너로 분기

각 job이 사설망 접속이 필요한지를 기준으로 러너를 나누려는 계획이었다.
그런데 정책을 하나씩 확인하다 보니 **세 환경 전부**에 같은 제한이 걸려 있었다.

전 구간이 제한된 환경이라면 러너를 나눠서 관리하는 복잡도가 오히려 손해였다.
그래서 **CI/CD 전 구간을 Self-hosted 러너로 통일**하는 쪽으로 정리했다.

---

## GitHub-hosted와 Self-hosted 차이

| 항목 | GitHub-hosted | Self-hosted |
| --- | --- | --- |
| 실행 위치 | GitHub 인프라 | 직접 관리하는 서버 |
| IP | 유동 | 서버 고정 IP (허용 목록에 등록 가능) |
| 사설망 접근 | 어려움 | 가능 |
| 인바운드 방화벽 | - | 열지 않아도 됨 (러너가 GitHub로 나가서 작업을 가져옴) |
| 관리 부담 | 없음 | 러너 업데이트와 서버 관리 필요 |

Self-hosted 러너는 러너가 GitHub에 아웃바운드로 접속해서 작업을 가져오는 방식이라
**서버의 인바운드 방화벽을 열지 않고도** 배포를 실행할 수 있다.
접근 통제 정책을 유지한 채 자동화할 수 있다는 점이 결정적이었다.

---

## Docker 사용

빌드와 실행 환경은 Docker로 통일했다.
서버마다 설치된 JDK나 라이브러리 버전에 영향받지 않고 같은 이미지로 배포할 수 있다.

설계 과정에서 오래된 OS(CentOS 7) 서버에서는 Node 20 기반 GitHub 액션이
glibc 버전 문제로 실패할 수 있다는 것도 확인했다.
컨테이너 안에서 실행하는 방식이 이런 호스트 OS 의존성을 피하는 방법이기도 했다.

---

## 시크릿은 두 곳으로 나눴다

시크릿을 쓰는 목적이 두 가지여서 저장 위치를 나눴다.

| 구분 | 용도 | 저장 위치 |
| --- | --- | --- |
| 파이프라인용 | 빌드, 배포 과정에서 필요한 값 | GitHub Secrets |
| 런타임용 | 서비스가 실행 중에 쓰는 값 (DB 접속 정보 등) | 서버의 `.env` |

파이프라인이 몰라도 되는 런타임 값은 GitHub에 올리지 않는다.
한 곳이 노출됐을 때 영향 범위를 줄이기 위한 분리다.

---

## Self-hosted 러너 보안

Self-hosted 러너는 **내 서버 위에서 워크플로 코드가 실행**된다.
GitHub-hosted 러너는 실행이 끝나면 사라지지만 Self-hosted는 서버가 그대로 남는다.
그래서 설계 단계에서 아래를 함께 검토했다.

- **외부 포크에서 온 PR 코드가 러너에서 실행되지 않게 한다.**
- **로그에 시크릿이 노출되지 않는지 확인한다.**
- **서드파티 액션을 쓸 때는 공급망 위험을 감안한다.**

---

## 워크플로 예시

구조는 아래처럼 러너 라벨만 지정하면 된다. (전체 예시가 아니라 형태만 보여준다.)

```yaml
jobs:
  deploy:
    runs-on: [self-hosted, dev]   # 환경별 라벨로 러너를 구분
    steps:
      - uses: actions/checkout@v4
      - name: Build and deploy
        run: docker compose up -d --build
```

- **개발, 운영, 온프레미스 고객사 서버 3개 환경 모두** Self-hosted Runner와 Docker 기반 파이프라인으로 구성했다.
- 수동 배포가 없어지고 자동 배포로 바뀌었다.

한 가지 부작용도 있었다.

별도로 볼륨을 증설해야 했다. 러너를 어디에 두느냐도 설계의 일부라는 걸 알게 됐다.

## 정리

이번 설계에서 배운 건 러너 종류를 고르는 일이 기술 취향이 아니라 **네트워크 정책에서 시작한다**는 점이다.

- 서버가 어떤 접근 제한 아래 있는지 먼저 확인한다.
- 그 제한을 유지한 채 자동화할 방법이 무엇인지 찾는다.
- 자동화 도구의 보안 위험은 제한을 푸는 쪽이 아니라 러너 운영 규칙으로 관리한다.
