## 배경

인수인계받은 디바이스 등록 모듈을 파악하다가 구조적인 문제를 발견했다.
기능은 동작했지만 이중화를 앞두고 있었고, 그 구조로는 이중화가 불가능했다.

코드를 바로 고치기 전에 **현재 구조를 문서로 먼저 정리**하고,
변경 설계를 별도 문서로 남긴 뒤 구현에 들어갔다.

---

## 기존 등록 흐름

```
1. 디바이스가 서버의 등록 확인 API를 HTTP로 호출
2. 서버가 그때부터 MQTT를 구독 (10초 대기)
3. 디바이스가 등록 정보 메시지와 상태 알림 메시지를 각각 MQTT로 발행
4. 서버가 두 메시지를 수신하고 검증
```

---

## 기존 구조의 문제

**1. 타이밍 레이스**
서버가 구독을 시작하기 전에 디바이스가 MQTT 메시지를 발행하면 메시지가 사라진다.
MQTT는 구독자가 없으면 메시지를 전달하지 않는다.

**2. 요청마다 SSL 핸드셰이크**
등록 요청이 올 때마다 MQTT 연결과 해제를 반복해서 핸드셰이크 비용이 매번 든다.

**3. HTTP 의존**
디바이스가 HTTP를 먼저 호출해야만 서버가 MQTT 수신을 시작한다.
MQTT로 통신하는 디바이스가 HTTP 호출에 의존하는 구조였다.

**4. 이중화 불가**
서버를 2대로 운영하면 두 인스턴스가 모두 메시지를 받거나, 둘 다 못 받는 경우가 생긴다.
어느 쪽이 구독하고 있는지를 서버 스스로 조율할 방법이 없었다.

---

## 재설계

### 상시구독으로 전환

서버가 기동될 때부터 계속 구독하도록 바꿨다.

- 서버가 기동되는 시점에 구독을 등록한다.
- 연결이 끊기면 자동으로 재연결한다.
- **재연결된 뒤에는 구독을 다시 걸어준다.**

마지막 항목이 중요하다.
재연결만 되고 구독이 복구되지 않으면 연결은 살아 있는데 메시지는 못 받는 상태가 된다.

### 메시지 하나로 합치기

기존에는 디바이스가 등록 정보와 상태 알림을 두 메시지로 따로 보냈다.
서버는 두 메시지가 모두 도착할 때까지 기다려야 했고, 이 수집 타이밍이 또 다른 문제였다.

디바이스가 **하나의 메시지로 합쳐서 발행**하도록 바꿔서 서버가 한 번에 검증하게 했다.
검증은 여러 단계로 나눠 처리하고, 결과를 디바이스에 다시 발행한다.

### 이중화 — Shared Subscription

AWS IoT Core의 Shared Subscription은 같은 그룹의 구독자 중 **한 곳에만** 메시지를 전달한다.

```
$share/<그룹명>/<토픽>
```

서버를 2대로 늘려도 같은 그룹으로 구독하면 메시지는 한 인스턴스만 받는다.
코드를 바꾸지 않고도 단일 서버와 이중화 환경에서 똑같이 동작하도록 **미리 대비**해 둔 설계다.

---

## 검증 쿼리 N+1 제거

재설계하면서 검증 로직도 함께 정리했다.

기존에는 검증 로직이 둘로 나뉘어 있었고,
메시지에 담긴 항목 N개를 하나씩 확인할 때마다 **항목마다 DB를 조회**한 뒤,
마지막에 전체 비교를 위해 한 번 더 조회했다. 총 N+1번의 쿼리였다.

```
기존   항목 1 → DB 조회
       항목 2 → DB 조회
       ...
       항목 N → DB 조회
       전체 비교 → DB 조회        (N+1번)

변경   기대하는 항목 전체 → DB 조회 1번
       항목 1..N → 메모리에서 대조
       빠진 항목 여부 → 메모리에서 확인   (1번)
```

기대하는 항목 목록을 한 번에 가져와 메모리에 올려두고 들어온 항목을 거기에 대조하는 방식이다.
DB 조회는 **N+1번에서 1번**이 됐고, 검증 로직도 하나로 합쳐졌다.

---

## 배포와 하위 호환

이중화 환경에서 함께 챙긴 항목들이다.

| 상황 | 대응 |
| --- | --- |
| 같은 메시지를 두 인스턴스가 중복 수신 | Shared Subscription |
| 처리 중 인스턴스 장애 | 디바이스가 timeout 후 메시지를 다시 보내 복구 |
| 롤링 배포 중 처리 중단 | graceful shutdown 설정 (종료 대기 30초) |
| 스케줄러 중복 실행 | 이번 범위 밖 (추후 분산 락 도입 예정) |

**기존 HTTP 방식의 등록 API는 삭제하지 않고 deprecated로 표시한 뒤 병행 운영했다.**
현장에 구 펌웨어가 남아 있는 동안은 옛 방식으로도 등록이 되어야 했기 때문이다.
구 방식의 정리는 구 펌웨어가 모두 교체된 뒤에 한다.

---

## 등록 결과 메시지 유실 — retain 적용

상시구독으로 바꾼 뒤에도 남는 문제가 있었다.
서버가 등록 결과를 발행한 직후에 디바이스가 구독을 시작하면 **그 메시지를 영영 받지 못한다.**
앱은 API로 다시 확인할 수 있었지만 디바이스에는 재확인 수단이 없었다.

MQTT의 **retain** 옵션은 마지막 메시지를 브로커가 보관했다가
나중에 구독한 쪽에게도 전달해 준다.
이 문제에 retain을 적용하는 것이 맞는지 위험(다른 발행 경로와 공유될 때의 부작용,
실패 결과가 오래된 상태로 전달될 가능성)까지 코드를 근거로 정리했다.

외부에서 받은 코드 리뷰 피드백도 바로 반영하지 않고
실제 코드 경로에 대입해 검증한 뒤 반영했다.
이후 팀 회의를 거쳐 등록 결과는 성공, 실패 구분 없이 retain을 적용하기로 결정했고,
테스트를 먼저 작성해 실패를 확인한 뒤 구현하는 방식으로 진행했다.
retain 메시지의 정리(만료) 방식은 별도 작업으로 분리했다.

## 결과

- HTTP 의존, 타이밍 레이스, 반복 SSL 핸드셰이크를 제거한 **상시구독 구조**로 전환했다.
- 등록 검증 DB 조회를 **N+1번 → 1번**으로 줄였다.
- Shared Subscription으로 단일 서버와 이중화 환경을 같은 코드로 운영할 기반을 마련했다.
- 구 펌웨어를 위해 기존 방식은 병행 운영 중이다.

새 흐름을 구현하고 테스트하다가 JPA 쓰기 순서 때문에 FK 위반과 Duplicate key 오류도 만났다.

## 정리

이 작업에서 남은 것은 코드보다 **"기존 구조가 왜 그렇게 되어 있는지를 먼저 이해한다"는 순서**였다.

- 인수인계 코드는 바로 고치지 말고 현황부터 문서로 정리한다.
- 문제를 "타이밍", "비용", "의존", "이중화"로 나눠서 각각 해결책을 대응시킨다.
- 이중화는 실제로 필요해졌을 때가 아니라 **설계할 때 미리 열어둔다.**
- 구 버전이 남아 있는 한 기존 인터페이스는 병행 운영한다.
