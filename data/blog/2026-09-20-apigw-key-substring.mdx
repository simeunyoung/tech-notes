## 상황

API Gateway 앞단에서 Lambda Authorizer가 `x-api-key` 헤더를 검증하고 있었다.
파트너사가 API를 호출할 때 쓰는 키였고, 키 하나를 여러 곳이 같이 쓰는 구조였다.

검증 코드를 읽다가 이상한 부분을 발견했다.
키가 **일치하는지**가 아니라 **포함되는지**를 비교하고 있었다.

---

## 원인

구조만 단순하게 옮기면 이런 코드였다. (실제 코드가 아니라 구조를 보여주는 예시다.)

```python
VALID_KEY = os.environ["API_KEY"]

def is_authorized(provided_key):
    return provided_key in VALID_KEY
```

파이썬에서 `a in b`는 `b` 안에 `a`가 부분 문자열로 들어 있는지를 확인한다.
그래서 정상 키 전체를 몰라도 일부만 넣으면 통과한다.

```python
"abcdef123" in "abcdef123"   # True  (정상 키)
"abcdef"    in "abcdef123"   # True  (앞부분만 알아도 통과)
"123"       in "abcdef123"   # True  (뒷부분만 알아도 통과)
""          in "abcdef123"   # True  (빈 문자열도 통과)
```

`==`로 비교해야 할 자리에 `in`이 들어가 있었던 것이다.
키가 노출되지 않았더라도 일부 조각만 추측해서 인증을 통과할 수 있는 구조였다.

---

## 실제 코드 확인

문서나 기억에 의존하지 않고, 지금 배포되어 있는 Lambda 코드를 CloudShell에서 직접 조회해서 확인했다.
분석은 그 코드를 기준으로 했다.

---

## 수정

`==`로만 바꿔도 이 버그는 막힌다.
하지만 공용 키 하나를 여러 파트너사가 같이 쓰는 것도 문제였다.
어느 한 곳에서 키가 새거나 문제가 생겨도 그 기업만 막을 방법이 없고,
누가 호출했는지도 알 수 없었다.

그래서 검증 방식을 바꾸면서 **기업마다 키를 따로 발급**하기로 했다.
Lambda 환경변수에 "키 값 → 회사명" JSON을 넣고, 들어온 키로 그대로 조회한다.

```json
{
  "키값A": "회사A",
  "키값B": "회사B"
}
```

```python
API_KEYS = json.loads(os.environ["API_KEYS"])

def authorize(provided_key):
    return API_KEYS.get(provided_key)   # 정확히 같은 키만 조회되고, 없으면 None
```

부분 문자열로는 조회가 되지 않으니 우회는 자연스럽게 막힌다.
조회 결과로 어느 회사의 호출인지도 알 수 있다.

호출 주체를 남기기 위해 API Gateway Access Log(JSON 형식)에 회사 식별 필드도 추가했다.
Lambda 코드, 환경변수 형식, 로그 형식을 정리해서 콘솔에서 직접 배포했다.

---

## 키를 환경변수에 둔 이유

키 목록을 어디에 저장할지도 정해야 했다.
호출하는 파트너사가 몇 곳 안 되는 규모라서 별도 저장소를 두기보다 **Lambda 환경변수에 JSON으로 넣는 쪽**을 택했다.

- 기업이 추가되거나 키를 회수할 때 환경변수만 수정하면 된다.
- 환경변수는 전체 합쳐서 4KB 제한이 있지만, 이 규모에서는 문제가 되지 않는다.
- 키를 여러 환경변수로 나눠 담아도 제한은 합산이라서 얻는 게 없다.

파트너사가 크게 늘면 그때 저장 방식을 다시 정하면 된다.

---

## 정리

- 인증 로직에서 **일치와 포함은 전혀 다른 비교**다. `in`이 들어간 검증 코드는 한 번 의심해볼 만하다.
- 키가 노출되지 않았더라도 조각만으로 뚫릴 수 있다는 점이 이 버그의 핵심이었다.
- 키를 기업별로 나누니 개별 회수와 호출 추적도 함께 가능해졌다.
